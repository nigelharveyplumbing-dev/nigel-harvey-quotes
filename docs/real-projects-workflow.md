# Real projects: authoring and future app workflow

## Current implementation

One reviewed JSON record in `business/project_content.json` supplies the shared layout in `business/real_projects.py` and styling in `static/real_projects.css`. Add records without copying page layout or adding a route per job. Content is a deliberately small public allowlist: no customer record, address, contact details, invoice, quote value or private app ID is passed to the renderer. Unknown fields fail validation.

Each record has a slug, title, area/town, service types, summary, starting condition, findings, work, optional known materials, result, staged photographs, alt text, captions, hero choice, optional approved review, related links, optional useful questions, SEO title and meta description. Canonicals use the established environment-aware `absolute_url`; do not put full host URLs into records. A review's `approved_for_use` defaults false. The Merrow record is opted in only because Nigel explicitly instructed use of that exact quotation.

`status=draft` is the default. Staff can inspect it at the final URL using the existing Basic Auth. Anonymous requests to a draft page or image return 404; staff responses use `private, no-store` and noindex headers. The draft is not listed publicly or in sitemap/backlinks. `/projects` shows no draft details to anonymous visitors, and an empty index is noindex. Staff index previews are also private/noindex. GA4 sending is disabled on draft/noindex pages even when the browser already has analytics consent. Staging keeps its existing whole-site staff-auth/robots protections, now supplemented by noindex response headers. `/app` and private API responses have explicit noindex headers.

Publication is a separate reviewed content change: set `status=published`, a real timezone-aware `approved_at`, a real `published_at`, and `updated_on` no earlier than publication. Set dates when publishing, not from the job completion date or the draft's creation date. Invalid or missing approval/date values fail startup. This is a code-review gate, not an authorization audit system: a future app must verify the approver's identity. No handler changes these fields, generates approval or publishes. Deployment still requires Nigel's separate explicit authorization.

After publication, the same record enables anonymous page/image access, the index card, project + index sitemap entries with meaningful lastmod dates, and reciprocal links on the six pages selected in the record. Existing content and schema on those service/location pages stay intact. No new tiling/shower service claims or pages are generated. The existing bathroom page is the natural shower link; radiators link to the heating plumbing page. Footer discovery leads to `/projects` from all shared public page families.

## Image process

All original job/customer photographs stay in Nigel's private owner files outside Git. The nine selected originals remain byte-for-byte in those files; they are not build or runtime dependencies. Never commit originals to this public repository, even when they contain no identifying metadata. The public manifest at `docs/project-images/merrow-ensuite/manifest.json` retains only source SHA-256/byte-count provenance and the cleared derivative IDs, dimensions, hashes and sizes. Private source filenames, storage paths and file/account IDs are not included. `.gitignore` blocks the old source directory and common original image formats in the project asset directory. Regression checks require exactly the cleared WebP derivatives and confirm the HTML preview embeds those same derivatives.

The initial unmerged Batch 6 commit mistakenly included nine original JPEGs under `docs/project-sources/merrow-ensuite`. Its branch history was replaced with a clean single commit directly on the unchanged main baseline; deleting the files in a child commit would not remove their history. That removes originals from the branch's reachable history, but GitHub may retain old commit/blob URLs after a force update. Do not treat a history rewrite as proof of server-side erasure. Owner follow-up through GitHub Support is required if old objects remain accessible; do not change main, unrelated refs or repository visibility to conceal this limitation. See [GitHub's removal guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

Public routes serve only explicit image IDs from the content record, at the two bundled WebP sizes. They cannot serve originals, a manifest, arbitrary static assets, invoice images or uploads. Apply EXIF orientation, preserve the full frame, resize to 640px and up to 1280px width, use WebP quality 86 and strip EXIF/XMP/IPTC. No generated or retouched evidence is used. Images retain intrinsic dimensions, responsive srcsets, descriptive alt text and captions; the finished-room hero is eager/high-priority and the remaining eight are lazy. Full-size selected WebPs remain linked for closer inspection. Future replacements should use new image IDs or purge the seven-day cache after an approved update.

## Future integration with the existing job pipeline (design only)

The baseline already has `jobs`, with `completed` in `business/job_pipeline.py`, linked to leads/quotes/invoices and exposed through authenticated `/api/jobs`. Add an optional **Use for website marketing?** action on completed jobs; completing, invoicing or paying a job must never publish anything.

1. Nigel opts in from the completed job. Create a private `job_marketing` record keyed by a unique `job_id`. Show existing draft/published page if the job has already been used.
2. Select only photographs cleared for marketing. Keep original private storage, separate derivative storage, consent basis and photo clearance notes. Strip metadata and flag faces, addresses, labels, documents and number plates for manual inspection.
3. Enter area/town and short public facts in a separate form. Do not copy the customer name, address, postcode, telephone, email, full job description, quote or invoice into generated prompts or public exports. Brand/product claims require recorded evidence. Distinguish observed symptoms from confirmed causes.
4. Review use is an explicit unchecked opt-in: exact text, permitted attribution, source and permission basis. Never pull a full customer name or Google account profile into public attribution automatically.
5. Generate a private draft case study, GBP post draft and social draft from that public fact set. No outbound posting capability runs here. Keep the fact sources and selected-image hashes with the draft revision.
6. Check duplicates: unique job ID + unique slug; compare normalized title/location/facts and overlapping image SHA-256/perceptual hashes with existing drafts and published projects. Flag probable matches for review; default to updating the existing project. Never mass-create service × area versions of one job.
7. Nigel approves a specific content revision and selected photos. Store `approved_by`, `approved_at` and the approved content hash; an edit after approval returns the record to draft. Separate approval for review use and for each GBP/social channel. Role-check every write with the existing staff auth/CSRF policy.
8. A deliberate Publish action exports that exact approved revision to the website content flow, or creates a reviewable branch/PR. Record canonical slug, publication/version, `marketing_used_at` and channel status. This is not a job-status trigger, scheduler or automatic post. No unauthorised deploy or repository push should be initiated by completing a job.

Suggested private statuses: `not_selected`, `draft`, `awaiting_approval`, `approved`, `published`, `withdrawn`. Keep an audit/history record; do not store internal job IDs in public JSON. An idempotent export uses the approved content hash so retries cannot create duplicate pages. Withdrawals remove sitemap/backlinks and decide an appropriate 404/410/redirect through review. Consent withdrawal and content corrections should have clear manual controls.

No database migration, pipeline UI change, job mutation, generator integration or social/GBP posting was implemented in this batch. This keeps quote/trade pricing and PR #4 isolated.

## Discovery and schema

New project pages use Article + BreadcrumbList and the existing single Plumber identity. The publisher/author is Nigel Harvey Plumbing; visible copy states that Nigel carried out the work. No qualifications or completion date are invented. Published dates appear both visibly and in Article JSON-LD; draft Article omits `datePublished`. FAQs are useful visible answers only, without claiming FAQ rich-result eligibility. Tristan's five-star quote is displayed exactly, including “radiation”, attributed only to “Tristan, Merrow”. No Review, Rating or AggregateRating schema is added.

Reference: [Google review snippet guidelines](https://developers.google.com/search/docs/appearance/structured-data/review-snippet) exclude self-serving LocalBusiness/Organization reviews from review snippets; [Article guidance](https://developers.google.com/search/docs/appearance/structured-data/article) describes matching visible headline/images/author/date information. JSON parsing and semantic regression checks are local; external Google Rich Results/Schema.org validator checks can follow on staging, without submitting production URLs now.

IndexNow is feasible with FastAPI, but not enabled here. An approved follow-up can generate a host ownership key and serve an exact UTF-8 key file on the canonical www host, then build a manual submission tool restricted to approved, publicly published URLs on that same host. Reject drafts, staging, `/app`, APIs, invoices, redirects and URLs with query strings. Default to dry-run; a deliberate approved notification submits the reviewed URL list and records the result. Do not send notifications from startup, sitemap reads, job completion or draft generation. [IndexNow documentation](https://www.indexnow.org/documentation) requires same-host key verification and explains keyLocation scope. IndexNow does not replace the sitemap or promise indexing. No key file, background sender or external notification was created.
